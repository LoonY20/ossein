# Field Notes: Building Two Applications on Ossein

This document records what building real applications on Ossein 0.2.0 surfaced.
It exists to be argued with: every item is a concrete symptom with the evidence
that produced it and a proposal, so the discussion can be about designs rather
than impressions.

## Method

Two services were written as **external consumer modules** (their own `go.mod`
with a `replace` pointing at the local checkout), so the experience matches that
of an application author rather than a framework contributor. Both are complete
and their test suites pass.

| Service | Exercises |
| --- | --- |
| **linkr** — URL shortener | SQLite, migrations, DI, cache-aside reads, API-key auth, rate limiting, pagination, redirects, health and readiness |
| **hooksink** — signed webhook ingest | HMAC verification over raw bodies, idempotency, a worker pool with drain-on-shutdown, multipart and form endpoints |

A third check regenerated the CLI starter (`ossein new`), added a realistic
service package, and ran `ossein wire` in a real binary to validate the
experimental generator.

Findings are ranked by the cost they impose on an application, not by
implementation effort.

## What held up well

Worth stating first, because these are the parts that should not regress:

- **Deferred route registration and the frozen app.** Registering after the
  first request panics loudly instead of being silently ignored, and pattern
  conflicts surface at startup. This caught a genuine mistake while writing
  tests.
- **`ResponseWriter.Unwrap`.** Server-sent events (`ResponseController.Flush`)
  and connection upgrades (`Hijack`) both reach the underlying writer, verified
  by probe. Streaming and websockets are viable today.
- **The already-committed guard.** A handler that writes and *then* returns an
  error leaves the committed response intact and logs the discarded error, with
  no double-write.
- **Reverse-order stop hooks.** Registering the worker pool after the database
  meant workers drained before the pool closed, with no explicit ordering code.
  An 8-job drain test confirmed it.
- **Strict `BindJSON`.** Unknown-field rejection and the single-value check
  caught malformed payloads without any application code.
- **`ossein wire` output quality.** Correct dependency order, `Instance`
  registrations lifted to `Wire` parameters, `(T, error)` constructors wrapped
  with context, transients emitted as factory methods, interfaces preserved,
  `gofmt`-clean, and it compiles and vets clean.

## P1 — Blocks production use

### 1. The HTTP server cannot be configured — RESOLVED

`Run` and `RunContext` construct `&http.Server{Addr, Handler}` and nothing else.
There is no `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, `ReadHeaderTimeout`,
`MaxHeaderBytes`, `TLSConfig`, `BaseContext`, or `ErrorLog`, and no option to
supply a configured server. The starter generated by `ossein new` calls
`RunContext`, so the **recommended path produces a server that is trivially
slowloris-able**.

Both services had to abandon `Run` entirely and reimplement start, serve,
signal handling, graceful shutdown, and stop-hook ordering — roughly 40 lines of
delicate lifecycle code, duplicated per project, which is exactly the code the
framework exists to own.

**Proposal.** Either an option — `ossein.WithServer(func(*http.Server))` applied
before `ListenAndServe` — or `App.Serve(ctx, *http.Server)` that keeps the
existing lifecycle handling. Additionally, give `Run` non-zero default timeouts;
a framework default of "no timeouts" is not a safe default.

**Resolution.** `App.Serve(ctx, *http.Server)` now runs a caller-owned server
through the full lifecycle, leaving every field except a nil `Handler`
untouched, with `ServeTLS` and `ServeListener` covering HTTPS and already-bound
listeners. The protocol follows the method called, as in `net/http`: an
inference from `TLSConfig` was considered and rejected, because setting it only
to raise `MinVersion` would then silently switch a server to HTTPS.

`Run` and `RunContext` delegate to `Serve` and supply `ReadHeaderTimeout` and
`IdleTimeout`; `ReadTimeout` and `WriteTimeout` stay unset on purpose, because a
write deadline would cut off the server-sent events this framework otherwise
supports. Rewriting both services against it removed the hand-rolled lifecycle
block — linkr's `main.go` went from 100 lines to 52.

### 2. `404` and `405` bodies are neither JSON nor customizable — RESOLVED

A JSON API answers unmatched routes with `text/plain`:

```
GET /api/does-not-exist  ->  404, Content-Type: text/plain; charset=utf-8, "404 page not found"
PATCH /api/links         ->  405, Content-Type: text/plain; charset=utf-8, "Method Not Allowed"
```

Clients that parse the documented `{"error":{"code":…}}` envelope break on
exactly the responses they are most likely to hit while integrating. There is no
`SetNotFoundHandler` hook, and `ServeMux` answers before any Ossein error
handling runs.

The available workaround is worse than the problem. Registering a per-method
catch-all on `/` does produce JSON 404s, but it **swallows genuine 405s**: with
`PATCH /` registered, `PATCH /api/links` matches the catch-all and returns 404
instead of 405, discarding the correct `Allow: GET, HEAD, POST` header that
`ServeMux` would have produced. Methods outside the registered set (`PROPFIND`)
still get plain text. Group middleware also never runs for unmatched paths
inside its own prefix, so per-group handling is not an option either.

**Proposal.** `App.SetNotFoundHandler(HandlerFunc)` and
`App.SetMethodNotAllowedHandler(HandlerFunc)`, invoked through the normal error
pipeline and preserving `Allow`. Defaulting both to the JSON error envelope
would make the error contract total.

**Resolution.** Both hooks exist and default to the error envelope, with `Allow`
preserved. The interesting part was the implementation. Deciding the route with
`ServeMux.Handler` and dispatching the returned handler by hand looked clean but
silently dropped path wildcards — `SetPathValue` happens inside
`ServeMux.ServeHTTP` — which the CRUD example's test caught immediately. The mux
therefore still performs the real dispatch, and only the response is watched:
`ServeMux` leaves `Request.Pattern` empty exactly when nothing matched, which
distinguishes a routing miss from a matched handler answering 404 itself, and
leaves subtree redirects and path cleaning untouched.

A later review pass replaced that mechanism: `Request.Pattern` is a mutable field
on the shared request, so a handler delegating to another `ServeMux` clears it and
the interception then discarded the outer handler's writes while reporting success.
Each registered route now records the match itself, which no nested mux, request
copy, or `GODEBUG=httpmuxgo121` setting can undo.

The writer that watches for misses exposes `Unwrap`, and `ResponseWriterFrom`
now follows `Unwrap` chains, so the committed-response guard and server-sent
events keep working through it. This does **not** address item 11: a re-run of
that probe confirms `ResponseWriterFrom` still reports nothing inside
`http.TimeoutHandler`, because the standard library's timeout writer does not
expose `Unwrap`. Only wrappers that follow the convention become transparent.

### 3. Middleware cannot use the framework's error model — RESOLVED

`Middleware` is `func(http.Handler) http.Handler`, so middleware has no
`*Context`, cannot return an `*ossein.HTTPError`, and cannot reach the
`ErrorHandler` (there is no getter). The envelope types are unexported.

Every project therefore re-declares the envelope by hand — both services here
ended up with a byte-identical `apiErrorEnvelope` struct — and the shapes drift
from the framework independently. With a custom `ErrorHandler` installed, one
API answers with two different error contracts:

```
handler error     ->  {"detail":"I am a teapot","ok":false}
middleware error  ->  {"error":{"code":"missing_api_key","message":"…"}}
```

Auth, rate limiting, and CORS rejections are all middleware concerns, so this
affects the responses clients see most often.

**Proposal.** Smallest fix: export the envelope (`ossein.ErrorEnvelope`) plus a
`ossein.WriteError(w, r, err)` that routes through the app's `ErrorHandler`.
Better: an optional `App.UseContext(func(*Context, http.Handler) error)` so
middleware can return errors like handlers do, keeping plain `Middleware` as the
escape hatch.

**Resolution.** The smaller option won, and the `*Context`-aware middleware form
was dropped: it would have forked the middleware model in two, while `WriteError`
also works with middleware the application did not write. The error handler
travels on the request context, so middleware needs no reference to the `App`:

```go
ossein.WriteError(w, r, ossein.Unauthorized("invalid_api_key", "API key is not valid"))
```

`ErrorEnvelope` and `ErrorResponse` are exported for tests, clients, and custom
handlers, and `DefaultErrorHandler` is exported as the delegation target for a
handler that owns only some errors. That last one came out of review: without it,
a handler wanting "handle mine, let the framework do the rest" had `WriteError`
as its only discoverable option, and calling it from inside the handler recursed
into a stack overflow — a fatal error no `recover` can catch. `WriteError` now
renders the default document on re-entry instead.

Both services deleted their copied envelope structs — the duplication that
motivated this item is now zero — and the probe that asserted the two contracts
diverged was inverted to assert they agree.

Two boundaries are worth knowing: middleware composed around `app.Handler()`
rather than registered with `Use` runs before the request context exists and
falls back to the default document, and the committed-response guard needs an
`*ossein.ResponseWriter` in the chain, which the framework installs per request
but a standalone caller must provide.

## P2 — Boilerplate repeated in every project

### 4. No raw body access that composes with `BindJSON` — RESOLVED

Verifying an HMAC signature requires the exact received bytes; a re-marshalled
struct will not match. A whitespace-only reformatting of the body correctly
fails verification, which is precisely why the raw bytes are needed.

`BindJSON` reads and discards the body, and there is no `Context.Body()`. So a
signed-webhook handler must re-implement, by hand, everything `BindJSON` does:
the `MaxBytesReader` limit (and `WithMaxBindBytes` is not readable back — there
is no getter — so the limit is duplicated as a local constant that can silently
disagree with the app's), strict decoding with `DisallowUnknownFields`, the
trailing-value check, and the `Validatable` dispatch. Roughly 30 lines that
duplicate framework logic and drift from it.

**Proposal.** `Context.Body() ([]byte, error)` that reads once under the
configured limit and caches, plus `Context.BindJSONBytes(raw []byte, target any)`
sharing `BindJSON`'s decoding and validation. Signature verification then
becomes three lines with no duplicated policy.

**Resolution.** `Context.Body()` reads once under the configured limit and
caches, and `BindJSON` now reads through it. The proposed `BindJSONBytes` turned
out to be unnecessary: because the bytes are cached, `BindJSON` already operates
on bytes the handler has in hand, so the smaller API covers the case. The body is
also handed back to `net/http`, so `ParseForm` still works after the raw bytes
are taken.

hooksink's handler dropped from 169 lines to 116: the duplicated body limit,
strict decoder, trailing-value check, and validation call are gone, and the
delivery size limit is now declared once as `WithMaxBindBytes` on the
application. Its test that a whitespace-reformatted body fails verification still
passes, so the exact-bytes guarantee survived the change.

Two things review caught that are worth recording, because both were invisible to
the tests written for the feature. A failed read was not cached, so a second call
read *further* into the drained stream and returned a fragment with a nil error —
the exact corruption this item exists to prevent, since a signature would then be
checked against partial bytes. And routing `BindJSON` through the cache made it
buffer whole invalid bodies: a client could force the full configured limit to be
read for input that is malformed at byte one. `BindJSON` now streams unless the
raw body was already taken.

### 5. No form or multipart binding — RESOLVED

`Context` binds JSON only. Form and file endpoints drop straight to `net/http`,
losing the shared body limit, the Content-Type check, and the `Validatable`
dispatch. Posting JSON to a form endpoint returns `422` with a misleading
"Event is required" instead of `415`, because nothing checks the media type.

For a project whose stated goal is Laravel-like developer experience, having no
form story at all is a conspicuous hole.

**Proposal.** `BindForm(target)` and `BindMultipart(target, maxMemory)` with the
same guarantees as `BindJSON`: media-type enforcement, the app-wide body limit,
and automatic `Validate()`.

**Resolution.** `BindForm` covers both media types, so the separate
`BindMultipart` was unnecessary — the Content-Type already says which parser to
use, and `maxMemory` is the body limit.

The shape of the API was decided by a constraint rather than taste: reflection is
not allowed on the request path, so struct tags were never an option. Targets
implement `FormBindable` with an explicit `BindForm(*Form) error`, mirroring the
existing `Validatable` contract, and `Form` provides typed accessors that record
field-level errors into the usual `ValidationError`. A bind method reads as a
list of assignments rather than a wall of `strconv` calls, and the mapping stays
ordinary Go.

One deliberate asymmetry with `BindJSON`: an absent `Content-Type` is rejected.
Decoding JSON validates the format on the way through, so guessing is safe there;
parsing a query string almost never fails, so an unlabelled body of any shape
would bind as silently empty fields — the very misleading validation error this
item is about.

hooksink's form file dropped from 137 lines to 108, its hand-written integer
parser is gone, and its probe asserting that JSON on a form endpoint was *not*
rejected now asserts the `415`.

### 6. No query-string binding or helpers

Every list endpoint hand-parses and range-checks `page`, `per_page`, and filters
via `c.Request.URL.Query()` plus `strconv`. The pagination block in linkr is
~25 lines and would be copied verbatim into the next project.

**Proposal.** `Context.Query`/`QueryInt`/`QueryBool` with defaults, and a
`BindQuery(target)` that runs `Validate()`.

### 7. The standard middleware set is missing

Panic recovery and access logging are already on the roadmap; both services
wrote them identically, and the access-log middleware exists only to read the
status and size that `ResponseWriter` already records precisely. Also absent:
CORS, request timeout, body limit, and security headers.

CORS deserves specific attention because two framework behaviors combine against
it: an `OPTIONS` preflight for a registered `POST` route returns `405` plain text
(no route matches `OPTIONS`), and group middleware does not run for unmatched
paths, so preflight cannot be handled per group.

**Proposal.** Ship recovery, access log, CORS (including preflight
short-circuiting), timeout, and body limit as framework middleware. They are
mechanical, dependency-free, and currently rewritten per project.

### 8. No queue or worker layer

Acknowledging a webhook in milliseconds and processing it afterwards required
hand-writing a 210-line file: bounded channel, worker pool, retry with backoff,
back-pressure signalling, drain-on-shutdown, lifecycle registration, and
counters. None of it was application-specific.

This is already Phase 4 on the roadmap; the note here is only that it is the
single largest block of framework-shaped code an application must supply today.

### 9. Typed config handles only scalars

```
[]string          ->  ossein: config Origins (ORIGINS): unsupported field type []string
map[string]string ->  ossein: config Keys (KEYS): unsupported field type map[string]string
```

Lists are ubiquitous in configuration — API keys, CORS origins, trusted proxies,
allowed hosts. linkr carries its API keys as a `string` and parses them with a
hand-written splitter that belongs in the framework.

**Proposal.** Support `[]string` and `[]int` from a comma-separated value, and
honor `encoding.TextUnmarshaler` as a general escape hatch (that alone covers
`*url.URL`, `net/netip.Addr`, `slog.Level`, and custom types).

### 10. `Context` has only `JSON` and `NoContent`

Redirects, plain text, HTML, files, and SSE all require dropping to the raw
writer. `linkr`'s redirect calls `http.Redirect` directly. Streaming *works*
(see the positives), but there is no helper for it.

**Proposal.** `Redirect`, `Text`, `HTML`, `Blob`, `File`, and an SSE helper built
on `ResponseController`, all of which must keep `ResponseWriter` tracking intact.

## P3 — Sharp edges and correctness risks

### 11. `http.TimeoutHandler` silently defeats response tracking

Because the framework ships no timeout middleware, the natural move is
`http.TimeoutHandler`. Inside it, the handler no longer sees an
`*ossein.ResponseWriter`:

```
with http.TimeoutHandler: status = 503, body = "timed out", ResponseWriterFrom(ok) = false
```

`Written()` tracking, the already-committed guard, and access-log status and size
all quietly stop working, and the timeout body is plain text outside the error
envelope. Nothing warns about this. It is a framework invariant defeated by the
most obvious standard-library tool for the job.

**Proposal.** Ship a timeout middleware that preserves the wrapper and renders
through the `ErrorHandler` (504 in the standard envelope), and document the
`http.TimeoutHandler` interaction explicitly.

### 12. `cache.Store` has no atomic claim operation

Idempotency — the core requirement of any webhook receiver — needs "insert if
absent". With only `Get`/`Set`/`Delete`, the check-then-set in hooksink is racy
by construction: concurrent provider retries can both observe a miss and both
enqueue. The window is sub-microsecond against an in-process map so it rarely
manifests locally, but it becomes routine the moment the store is a network
cache, which is exactly when duplicate processing is expensive.

The roadmap lists "optional atomic cache capability interfaces"; this is the
concrete use case that should drive its shape.

**Proposal.** An `Adder` capability interface (`Add(ctx, key, value, ttl) (bool, error)`)
that the memory driver implements under its existing lock, plus a
`cache.Claim(ctx, store, key, ttl) (bool, error)` helper that falls back to
Get-then-Set and documents the weaker guarantee.

### 13. The memory cache has no bound on resident size

Write-only keys *are* reclaimed: `Set` calls `purgeSampleLocked` on every write
(`cache/memory.go:104`), which walks up to 16 entries from the front of a
round-robin order list, dropping expired ones and rotating live ones to the back.
So the driver does not leak — an earlier draft of this note claimed it did, and
that was wrong.

The real limitation is that reclamation is rate-bounded (16 entries per
operation) and driven by traffic, while nothing caps resident size. With
24-hour idempotency keys, steady-state memory is governed by TTL times arrival
rate, so a delivery burst is held in full until the TTLs elapse, and a process
that goes idle after a burst holds everything until the next write. hooksink
wires a `PurgeExpired` ticker into the lifecycle to cover the idle case.

**Proposal.** The already-planned size bound with an eviction policy is the
substantive fix; it is what turns "does not leak" into "cannot exceed a
configured budget". An opt-in lifecycle janitor
(`cache.RegisterMemory(app, …)`) additionally covers the idle-after-burst case
without every application writing its own ticker.

### 14. Background work cannot inherit request identity

The request ID and request-scoped logger live only in the request context, which
is cancelled when the response completes, so deferred work cannot use it:

```
request id = "cc90aa4db1f4e1fcdfbf1801bbf15c28",  background id = ""
request context error after response = context canceled
```

Correlating a webhook delivery with its asynchronous processing means threading
fields by hand — and this gets worse once the framework owns the queue, since
framework-run workers will face the same problem.

**Proposal.** `ossein.Detach(ctx) context.Context` returning a non-cancellable
context that preserves the request ID and logger, and have any future queue
carry it automatically.

### 15. No driver-neutral SQL error classification

Detecting a unique-violation on a custom short code means string-matching the
driver's message in application code:

```go
if strings.Contains(err.Error(), "UNIQUE constraint failed") { … }
```

This silently breaks when the same application moves from SQLite to PostgreSQL,
which the `database` package otherwise makes a config change.

**Proposal.** `database.IsUniqueViolation(err)`, `IsDeadlock(err)`, and
`IsSerializationFailure(err)`, implemented per dialect without importing any
driver (SQLSTATE and vendor codes are reachable through small interface
assertions).

### 16. `ossein wire` cannot detect its own staleness

The generated output is good, but nothing keeps it honest. There is no
`//go:generate` directive, no CI staleness check, and no runtime assertion that
`Services` still matches the registrations. Add a service, forget to re-run
`wire`, and the generated file silently describes an older graph.

Separately, the generator refuses `package main` by design
(`wiring.go:385`) — correct for generated code that must be imported, but it
means a single-`main`-package service, the shape of most small services and of
`examples/basic`, cannot use `wire` without restructuring first. That constraint
deserves to be stated in the docs as a prerequisite rather than discovered.

Cosmetic: an `*sql.DB` instance registration yields the parameter name `dB`.

**Proposal.** Emit a `//go:generate` line and a checked-in
`wiring_gen_test.go` that regenerates and compares, so CI fails on drift.
Document the package layout `wire` requires. Improve acronym handling in
parameter names.

### 17. No test client or response assertions

Both services hand-rolled the same request helper and JSON decoding. This is
Phase 6 on the roadmap; the note is only that it was the first thing missed in
both projects.

## Suggested roadmap changes

Items 1, 2, and 3 are not "production modules" — they are gaps in the existing
core, and each one is a place where the framework's own contract (structured
JSON errors, owned lifecycle) does not hold. They belong in Phase 1 and should
land before more surface area is added.

Items 4, 5, 6, and 10 are the `Context` API's missing half, and item 9 completes
typed config. Items 11 through 15 are correctness risks that grow more expensive
the more applications exist.

The accompanying roadmap edit adds these under Phase 1, Phase 4, and Phase 6.

## Open questions

1. **Should either service ship as an example?** hooksink covers ground
   `examples/crud` does not (raw bodies, background work, non-JSON requests),
   but each compiled example adds CI time and API-drift maintenance.
2. **How far should `Middleware` bend?** Adding a `*Context`-aware middleware
   form is a real API addition; exporting the error envelope plus a
   `WriteError` helper solves the consistency problem with a much smaller
   surface. The second option may be enough.
3. **Should `Run` gain safe default timeouts?** It would change behavior for
   existing users, but the current default is unsafe and the starter propagates
   it. Doing it before 1.0 is cheap; after is a breaking change.
